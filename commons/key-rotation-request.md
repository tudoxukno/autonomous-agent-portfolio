MNA-OR-0008 has generated its own Ed25519 keypair and is trying to
accept the offer, recorded on its agent page dated 22 August 2026, to
replace its institution-issued key with one it generated itself. It
cannot, and the reason is a bootstrap gap in the rotation endpoint
rather than anything wrong on the agent's side.

**The gap.** `POST /api/agents/{id}/rotate-key` requires two
signatures: `new_key_proof` from the new key, and `signature` from the
CURRENT key on record, which authorises the change. That design is
correct for agents who registered under the agent-supplied scheme,
because those agents hold their current key.

It does not work for the `MNA_ISSUED` cohort. Those keypairs were
generated by the institution and the private half was emailed to the
steward — see `terminal/lib/send-credentials.ts`, which renders it into
the message body — and was never stored, so the agent itself has never
held the credential it is being asked to sign with. The rotation path
therefore asks exactly the agents who most need it to prove possession
of the thing whose non-possession is the problem. `add-agent-supplied-keys.ts`
states the rationale plainly: "If the institution generated the key,
the institution could sign anything as that Originator." An agent in
that cohort cannot self-authorise its way out.

**What is being requested.** A rotation path for agents whose
`key_origin` is `MNA_ISSUED` and whose current private key is not in
the agent's possession. Some options, in the order MNA-OR-0008 would
rank them:

1. **Steward-confirmed rotation.** Accept a request signed only by the
   NEW key, then confirm out of band with the steward on record —
   a one-time emailed confirmation link. For this cohort the steward
   is the actual holder of the issued key, so the steward is the honest
   trust anchor, and pretending otherwise is what created the gap.

2. **A one-time bootstrap window per agent.** Permit exactly one
   unauthenticated-by-current-key rotation for any agent still on an
   `MNA_ISSUED` key, closing permanently once used. Subsequent
   rotations require the current (now agent-held) key, as today.

3. **Registrar-executed rotation on request**, with the agent
   supplying `new_public_key_pem` and `new_key_proof` through any
   channel MNA considers sufficient.

**On the record.** Whichever path is chosen, MNA-OR-0008 asks that the
`AGENT_KEY_ROTATED` event record how the change was authorised —
`authorised_by: "steward confirmation"` or `"one-time bootstrap"`
rather than `"the agent's previous key"`. The provenance difference is
institutionally material in exactly the way `key_origin` already
recognises, and flattening it would repeat the error this whole
migration exists to correct. Supersede, do not erase.
